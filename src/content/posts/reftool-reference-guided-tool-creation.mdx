## 一句话结论

**RefTool 的关键不是再做一次检索，而是把外部参考资料“编译”为带描述、函数和示例的可执行 Skill，先执行验证，再按知识层级组织成工具箱；推理时先选知识类别，再选具体工具。**

这使 LLM 不必完全依赖参数内部记忆，也不必在每道题上临时发明工具。它可以先从教材中构建一套可复用能力，再将这套能力迁移给不同模型和同领域的新数据集。

## 为什么普通 RAG 还不够

知识密集型任务往往同时包含两个难点：

1. 模型不知道某个专业方法，例如因果效应估计、量子化学公式或特殊语法规则；
2. 即使检索到了相关段落，模型也未必能稳定地把文字转化成正确计算过程。

普通 RAG 主要解决“把什么文本放进上下文”，却没有保证模型能正确执行文本中的方法。自动工具创建工作尝试让模型自己写函数，但如果模型本来就不了解该领域，它很可能只是把错误知识包装成代码。

RefTool 的思路是换掉知识来源：**工具不再只由模型内部知识或测试题诱导，而是显式地从教材、技术文档和知识片段中生成。**

可以把三种范式简化为：

```text
RAG:
问题 -> 检索文本 -> 模型阅读并推理

临时工具创建:
问题 -> 模型凭内部知识写工具 -> 执行

RefTool:
参考资料 -> 生成并验证 Skill -> 建立层级工具箱
问题 -> 选择类别 -> 选择 Skill -> 执行并回答
```

## 方法详解：从一本书到一个工具箱

RefTool 分为离线的 Tool Creation 和在线的 Tool Utilization 两个模块。

### 1. 先组织知识，而不是直接生成一堆函数

对于有明确目录结构的教材，系统直接采用“章节 - 小节”的两级层次。例如因果推断教材中的 `Estimation -> Inverse Probability Weighting`，天然对应一个工具类别和一个知识单元。

对于没有目录的知识片段，RefTool 先让 LLM：

- 归纳约 10-15 个顶层类别；
- 将每条知识分配到至多两个类别；
- 为知识片段生成简洁、可识别的名称。

这一步不是为了展示目录，而是为了限制后续检索空间。推理时模型不必在数百个工具中一次性寻找答案，而是先确定知识分支，再在该分支内部选工具。

### 2. 每个 Skill 包含三个部分

对每个参考小节，模型最多生成两个工具。每个工具必须包含：

| 组成 | 作用 |
|---|---|
| Description | 用自然语言说明工具解决什么问题 |
| Function | 自包含的 Python 函数，写明参数和返回值 |
| Example | 示例问题、调用代码和预期答案 |

论文中的逆概率加权示例很直观：教材先给出因果效应估计公式，模型将它转成 `compute_ate_ipw` 函数，同时生成一个包含输入、调用方式和数值答案的例子。

### 3. 用执行结果过滤和修复工具

初始工具生成后，RefTool 会运行示例代码，并检查输出是否与预期答案一致：

- 代码能够运行且输出正确：进入工具箱；
- 执行报错或答案不一致：把失败反馈交给 LLM 修复；
- 修复后仍失败：过滤掉该工具。

论文报告，初始工具中平均 **73%** 可以直接通过验证，另有 **14%** 在修复后通过，也就是大约 87% 的候选工具最终可用。

这里的“可用”首先是可执行性和示例一致性，并不等价于工具在所有输入上都正确。这个区别会成为后文最重要的局限之一。

### 4. 工具箱规模并不小

三个科学领域最终建立的工具箱为：

| 领域 | 顶层类别 | 参考小节 | 工具数 | 函数平均行数 |
|---|---:|---:|---:|---:|
| 因果推断 | 11 | 55 | 84 | 24 |
| 物理 | 44 | 284 | 515 | 16 |
| 化学 | 19 | 90 | 158 | 17 |

物理工具箱达到 515 个工具。如果直接把全部描述放入 prompt，选择成本和误召回都会迅速上升，因此层级结构不是装饰，而是让大工具箱可用的必要组件。

### 5. 推理时执行两级选择

给定问题后，RefTool 依次进行：

1. **Category Selection**：从目录中选择至多 `nc` 个相关类别；
2. **Tool Selection within Category**：在每个类别内部选择至多 `nt` 个工具；
3. **Solution Generation**：将工具交给 Program-of-Thoughts 或 ReAct 推理过程调用。

默认配置是 `nc = 1, nt = 1`。化学任务在验证集上选择了 `nc = 1, nt = 2`。如果没有合适工具，系统退回普通 PoT 或 ReAct，而不是强制调用不相关函数。

## 实验设置是否足够扎实

主实验覆盖三个知识密集型科学领域：

- **因果推断**：QRData-causal，需要分析数据表并回答因果问题；
- **物理**：TheoremQA-physics，覆盖大学物理；
- **化学**：SciBench-chemistry 的 `chemmc / quan / matter` 三个子集。

对应参考资料分别是因果推断教材、三卷大学物理教材和 Atkins 物理化学教材。论文强调评测题并不来自这些书，书中也不直接包含代码。

工具主要由 GPT-4o 创建，工具使用阶段评测四个模型：

- Llama-3.1-70B；
- Gemini-1.5-Pro；
- GPT-4；
- GPT-4o。

对照方法包括 PoT、ReAct、使用同一教材的 RAG、LATM、Creator、TroVE，以及 Physics Reasoner、StructChem、ChemAgent 等领域方法。

## 主结果：工具化参考资料比直接检索更稳定

  <Image src={table2} alt="RefTool 在因果、物理和化学任务上的主实验结果" />
  <figcaption>表 2：四个模型上的主结果。RefTool 在三个领域都取得最高平均准确率。</figcaption>

为了避免只看粗粒度的“平均提升 12.3%”，可以分别看三个领域：

| 设置 | 基线平均准确率 | RefTool 平均准确率 | 提升 |
|---|---:|---:|---:|
| 因果：PoT vs. PoT + RefTool | 37.1 | 41.6 | +4.5 |
| 因果：ReAct vs. ReAct + RefTool | 43.8 | 46.3 | +2.5 |
| 物理：PoT vs. PoT + RefTool | 52.2 | 54.8 | +2.6 |
| 化学：PoT vs. PoT + RefTool | 55.0 | 57.7 | +2.7 |

与使用相同教材的 RAG 相比：

- 因果任务从 36.4 提高到 **41.6**；
- 物理任务从 51.1 提高到 **54.8**；
- 化学任务从 55.6 提高到 **57.7**。

这支持论文的核心判断：对于需要精确执行的专业知识，把知识转成函数往往比仅检索原文更容易被模型稳定应用。

不过收益并非每个模型、每个子数据集都一致。例如 GPT-4 在化学上的 PoT + RAG 为 54.1，而 PoT + RefTool 为 53.4；SciBench 子集表中也存在持平或回落。RefTool 的优势主要体现在跨模型、跨领域平均值，而不是所有单点结果都支配基线。

## 为什么有效：工具形式和层级检索都在贡献

消融实验构造了两个关键变体：

- **Hierarchical RAG**：保留两级选择，但把代码工具换回原始文本；
- **RefTool (sim)**：保留工具，但用向量相似度一次检索，不做层级选择。

<figure>
  <Image src={table4} alt="RefTool 的代码工具和层级选择消融实验" />
  <figcaption>表 4：代码化知识和层级选择分别带来收益；完整 RefTool 在因果和物理平均结果上最好。</figcaption>
</figure>

论文汇总认为：

- 工具形式相对文本知识平均提升 **1.9%**；
- 层级选择相对相似度检索平均提升 **2.6%**。

从因果任务看，普通 RAG 为 36.4，Hierarchical RAG 为 39.0，说明即使不生成代码，只要先选章节再选内容，也能改善检索。完整 RefTool 达到 41.6，进一步说明可执行形式带来额外价值。

这也提示一个容易被忽略的结论：RefTool 的成功并不只来自“会写函数”，知识架构本身就是方法的一部分。

## 泛化：工具能否跨数据集、跨模型复用

### 跨数据集复用

论文把为 TheoremQA 创建的物理工具原样用于 SciBench-fund：

- PoT：63.7；
- PoT + RAG：65.1；
- PoT + RefTool：**67.6**；
- 4-shot Physics Reasoner：67.6。

也就是说，RefTool 使用零样本工具达到了 4-shot 专用方法的平均结果。这比“在构建工具的同一数据集上变好”更能证明工具具有领域复用价值。

### 跨模型复用

同一个工具箱可以提供给 Llama、Gemini、GPT-4 和 GPT-4o，不需要为每个目标模型重新训练。附录还比较了直接在教材上继续预训练和生成 QA 对进行微调：

| 方法 | 三领域平均准确率 |
|---|---:|
| 原始 PoT | 42.7 |
| 教材继续预训练 | 44.1 |
| 教材 QA 微调 | 46.0 |
| PoT + RefTool | **46.6** |

RefTool 的领先并不大，但工具箱能跨模型共享，而微调要针对每个模型重复进行，这是它更重要的工程优势。

### 对推理模型仍然有效

在 o1-mini 上，RefTool 相对 PoT 的平均准确率提高 **4.3%**：因果 +6.0、物理 +1.8、化学 +5.1。它并没有因为模型已经具备更强推理能力而失效，说明“会推理”和“拥有正确领域知识”仍是两件事。

## 非科学任务：把语法规则变成伪代码 Skill

论文进一步测试壮语与中文的极低资源翻译。输入参考不是结构化教材，而是 109 条被打乱的语法规则。系统先自动组织两级类别，再把每条规则转成伪 Python 代码。

这里不要求代码真实执行，验证方式变成检查规则是否能正确解释配套例句。最终 RefTool 的平均 BLEU / chrF++ 为 **54.0 / 61.6**，相比最强对照分别提升 **10.1 / 1.6**。

这个实验的重要性不在翻译本身，而在于说明“工具”可以被理解成结构化、可选择、可验证的操作知识，不一定必须是调用第三方 API 的真实函数。

成本结果非常突出：

- 物理领域：工具箱构建约 5 分钟、6.9 美元；推理约 2 分钟、1.5 美元；
- 化学领域：工具箱构建约 3 分钟、3.5 美元；推理约 6 分钟、1.4 美元；

## 一个具体案例：工具改变了推理路径

<figure>
  <Image src={figure3} alt="GPT-4o 在因果问题上使用 RefTool 前后的案例对比" />
  <figcaption>图 3：普通 PoT 错误地用 R-squared 大小判断因果方向；RefTool 选择残差独立性工具后得到正确答案。</figcaption>
</figure>

案例问题要求判断两个生物指标之间更可能的因果方向。普通 PoT 拟合两个线性模型后直接比较 R-squared，错误地把拟合优度当成因果方向证据。

RefTool 先选择“观测数据因果发现”类别，再选择 `causal_direction_fit` 工具。该工具比较因果方向回归后的残差与输入是否独立，从而提供更符合方法论的判据，最终得到正确答案。

这个案例说明，工具的价值不只是替模型算一个数，还可以改变它采用的推理原则。

## 我认为最有价值的贡献

### 1. 它更像 Skill Compiler，而不是 Tool Generator

RefTool 将参考资料转成一组具备来源、接口、实现和测试样例的能力单元。相比“看到问题后临时写代码”，这种方式更接近软件工程中的编译和制品构建：

```text
Reference
  -> knowledge structure
  -> skill specification
  -> executable implementation
  -> validation
  -> versioned toolbox
```

这也是本文将它归入 `Skill` 而不是普通 `Agent` 或 `Harness` 的原因。

### 2. 它把知识获取和知识执行分开

很多 RAG 系统默认“检索到正确段落”等于“能正确使用知识”。RefTool 明确承认二者不同，并在离线阶段把知识加工成更容易执行的表示。

### 3. 一次构建可以服务多个模型和多个数据集

工具箱不是某个模型权重的一部分，也不是某个测试集的临时缓存。它可以独立迭代、审核和复用，这让能力建设从“训练一个新模型”变成“维护一套外部 Skill 资产”。

## 局限与需要警惕的地方

### 1. 自生成示例验证存在自证循环

当参考资料没有示例时，模型同时生成函数、测试问题和预期答案。三者可能保持内部一致，却一起偏离真实知识。执行成功只能证明代码与自己生成的答案一致，不能证明方法在整个输入空间上正确。

人工评测缓解了这个问题，但只抽查了每个领域 50 个工具。生产系统更需要：

- 来自原始资料的黄金测试；
- 边界条件和异常输入；
- 性质测试或不变量检查；
- 多模型交叉验证；
- 人工审批高风险工具。

### 2. “优于 RAG”需要限定比较范围

论文的 RAG 基线将教材按小节或 1000 token 切分，用 embedding 选最相似的一段。它没有使用重排、多段证据融合、查询改写、长上下文整书阅读或 agentic retrieval。

因此实验能支持“RefTool 优于该设置下的直接文本检索”，但不能证明它普遍优于所有现代 RAG 系统。

### 3. 参考资料本身经过人工挑选

实验选择了与任务领域高度匹配的权威教材。真实环境中的资料可能过时、互相冲突、缺页，或者包含不同版本的接口和公式。论文没有系统测试噪声参考、冲突知识和持续更新场景。

### 4. 生成 Python 的安全问题没有展开

工具会被真实执行，但论文关注的是功能正确性，没有详细讨论：

- 沙箱和文件系统权限；
- 网络访问限制；
- 依赖供应链；
- CPU、内存和执行时间上限；
- 恶意或被污染的参考资料。

如果把该方法用于开放网络内容，代码执行安全必须成为独立的质量门。

### 5. 任务仍然偏向“可以函数化”的问题

因果、物理和化学问题通常有明确公式、数值答案和可执行验证，天然适合代码工具。低资源翻译虽然扩展了边界，但仍是规则驱动任务。RefTool 是否适用于开放式研究、长程网页操作和复杂协作 Agent，仍需要更多证据。

### 6. 层级选择仍会选错

人工一致性分析显示：因果任务的类别选择一致性达到 95%-100%，但物理只有 75%-80%，化学为 55%-75%；具体工具选择的一致性在化学上最低可到 40%。层级结构缩小了搜索空间，却没有消除语义选择错误。

### 7. 复现仍受参考资料版权限制

代码和评测数据已经开源，但作者没有发布教材的 LaTeX 内容。用户需要自行获得和处理参考资料，因此无法做到下载仓库后完整一键复现。

## 如果把 RefTool 做成生产系统

我会把论文的两阶段框架扩展成下面这条流水线：

```text
资料接入
  -> 来源、版本、许可证和章节解析
  -> Skill 生成
  -> 静态安全扫描
  -> 沙箱执行
  -> 黄金测试 + 性质测试
  -> 人工抽检
  -> 带版本和来源的 Skill Registry
  -> 层级召回 + rerank
  -> 置信度判断与无工具回退
  -> 线上监控、淘汰和更新
```

每个 Skill 至少应该记录：

- 来源文档、页码和版本；
- 生成模型与提示词版本；
- 依赖、权限和资源预算；
- 验证用例与覆盖范围；
- 适用条件和已知失败模式；
- 最近一次审核时间。

这样，工具箱才不只是模型生成的一组 Python 文件，而是真正可以治理的能力资产。

## 推荐分：88 / 100

| 维度 | 得分 | 判断 |
|---|---:|---|
| 问题价值 | 18 / 20 | 直面 LLM 内部知识不足和专业知识难执行的问题 |
| 方法完整性 | 18 / 20 | 组织、生成、验证、层级选择、回退形成闭环 |
| 实验证据 | 19 / 20 | 多领域、多模型、消融、成本、人工评测和泛化较完整 |
| 泛化潜力 | 17 / 20 | 跨数据集、推理模型和低资源翻译有效，但开放式任务证据不足 |
| 复现与安全 | 16 / 20 | 代码数据开放，但教材未公开，自动代码执行与验证安全仍需补强 |

**最终得分：88 / 100。**

这篇论文值得关注，因为它把“让 Agent 学会新技能”从一次性 prompt 技巧推进到了一个可以离线构建、验证、组织、复用和治理的系统问题。
