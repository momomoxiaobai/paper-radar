## 一句话结论

**RoboArchitect 不更新 VLA 权重，而是让编码模型观看完整失败轨迹，反复改写策略外面的 Harness：什么时候相信原策略、什么时候调用视觉工具、什么时候直接接管机械臂、什么经验要跨 episode 记住，都由执行证据逐轮塑造。最多五轮后，平均未见场景成绩从 9.7% 提高到 43.3%，未见任务从 12.7% 提高到 40.2%。**

## 为什么“模型不行”可能其实是 Harness 不行

机器人策略通常被当作系统的主体：输入相机、深度、关节和指令，输出动作。如果失败，第一反应往往是继续收集演示、微调权重或换更大模型。

但真实机器人 Agent 并不只有模型。模型外面还有一层决定执行方式的程序：

- 如何把像素与深度投影到三维坐标；
- 卡住时是否回退、抬升或重试；
- 是否调用检测、分割、指向或抓取姿态模型；
- 什么时候让 VLA 继续控制，什么时候用程序动作接管；
- 如何把上一次成功的抓取高度带到下一次任务。

这些 glue code、控制流、工具协议和状态共同构成 **Agent Harness**。RoboArchitect 的研究问题不是“能否训练一个更好的机器人模型”，而是：**能否把 Harness 本身变成自动优化的程序制品？**

## 系统循环：用执行结果改写执行系统

RoboArchitect 从最简单的 pass-through Harness 开始：直接返回冻结策略给出的动作。随后重复以下循环，最多五轮：

```text
当前 Harness 在训练 episodes 中执行
-> 记录每一步图像、深度、机器人读数、动作和工具输出
-> 编码模型阅读完整 rollout
-> 诊断反复出现的失败模式
-> 改写 Harness 程序
-> 在相同训练 episodes 上重新评估
-> 只有成绩提高才接受新版本
```

这里的“训练”只训练 Harness，没有任何模型权重更新。最终版本在独立的 held-out episodes 上评估，避免把训练场景中的物体坐标直接写进代码后冒充泛化。

编码模型可以使用多种辅助能力：语言模型、视觉语言模型、Grounding-DINO、SAM 3、指向模型、GraspGen、三维投影和轨迹原语。重要的是，论文没有预先规定一套固定 Agent 架构；编码模型可以自己决定调用哪些工具、采用什么控制流。

### 接受规则到底保证了什么

这篇论文的核心贡献主要是系统与实证，作者没有提出一个需要反向传播求解的中心学习目标。为了把 Algorithm 1 的版本接受逻辑写清楚，可以把它**工程化形式化**为下面的选择规则；这不是论文声称的新数学公式：

```text
          { H′k,  若 Jtrain(H′k) > Jtrain(Hk)
Hk+1  =  {
          { Hk,   否则
```

其中：

- `Hk` 是第 `k` 轮已经接受的 Harness；
- `H′k` 是编码模型根据本轮 rollout 生成的候选程序；
- `Jtrain(H)` 是固定训练 episodes 上的任务成功率，而不是语言模型打分；
- 严格大于号意味着没有观测到训练收益的补丁会被丢弃。

因此，`Jtrain(Hk)` 随接受轮次单调不降，但这**不推出** `Jheld-out(Hk)` 也单调不降。训练 episodes 只是有限的行为样本；新分支可能记住物体位置、为某一种失败过度接管，或破坏训练集中未覆盖的原策略能力。论文中 RLDX-1 在 RoboCasa-365 上从 27.9% 轻微降到 27.8%，正是这个逻辑边界的实证提醒。

## Harness 最终学会了什么

### 1. 针对失败模式生成控制补丁

论文给出的典型例子非常具体：

- 原策略持续顶住障碍物时，检测机械臂 jam，先抬升脱困再重新询问策略；
- 顶部接近会撞到隔板时，生成侧向伸入的运动原语；
- 关门力量太小时，放大接触动作幅度；
- 策略总去训练数据中的旧位置时，用指向/检测工具重新定位指令中的对象；
- 移动底盘漂离工作区时，把底盘限制在活动区域；
- 候选目标不可靠时，按排序尝试并用深度确认抓取是否成功。

这些不是抽象的“反思文字”，而是下一版 Harness 里的可执行条件与控制程序。

### 2. 动态决定模型控制权

Harness 并不总是让程序替代 VLA。不同设置下会形成三种状态：

| 策略状态 | Harness 行为 |
|---|---|
| 原策略已接近目标 | 保留策略控制，避免破坏原有能力 |
| 原策略局部失败 | 程序短暂接管，恢复后交还控制 |
| 原策略完全失效 | 演化为视觉驱动的 code-as-policy Agent |

例如通用 X-VLA 在 SimplerEnv WidowX 上始终输出完全张开的夹爪，Harness 最终完全忽略原策略，自己完成视觉定位、运动与抓取；而包裹已经微调好的 specialist 时，统一 Harness 大体保留原策略，只在失败信号出现时介入。

这比固定 fallback 更有价值：**控制权分配本身也是从 rollout 中学习出来的。**

同样，为了明确“模型控制”与“程序接管”的关系，可以把每一步动作写成如下工程抽象：

```text
      { πVLA(ot),                    若 gt = policy
at =  {
      { fharness(ot, mt, tools),     若 gt = program
```

`o_t` 是图像、深度、机器人状态和指令组成的当前观测，`g_t` 是 Harness 计算出的控制权门变量；`π_VLA` 是冻结策略，`f_harness` 则可以调用视觉模型、几何工具和运动原语。关键不是永远二选一，而是程序可以短暂接管脱困，满足恢复条件后再把控制权交还给 VLA。

### 3. 自发形成持久记忆

论文没有给定 memory schema，但几乎所有设置都演化出跨 episode 保存的数据结构，包括：

- 成功抓取点距离物体顶部的深度；
- 夹爪应在物体高度的什么比例处闭合；
- 某种物体适合 pinch 还是 spread grip；
- 哪类指令需要持续抓住物体；
- 仿真环境多少步会重置；
- 不同机器人手指的闭合方向与静止位置。

这些记忆不是编码模型对话上下文，而是最终机器人 Agent 内部的运行时数据结构。每次评测从空记忆开始，Agent 在 held-out episodes 中自行积累。

其跨 episode 更新可以概括为：

```text
mt+1 = U(mt, ot, at, outcomet)
```

这里 `m_t` 是执行前的持久记忆，`outcome_t` 包含抓取是否成功、是否卡住、目标深度和任务终止信号，`U` 是演化后 Harness 中实际生成的写入逻辑。论文的重点不是给 `U` 一个统一神经参数化，而是让代码模型从失败轨迹中发现“哪些量值得存、何时更新、下次如何读”。

五个代表性设置中，平均每个 episode 会读取记忆 3.4 到 13 次，找到可用记录的比例为 **92% 到 99%**。这说明记忆并非展示用日志，而是实际参与动作决策。

## 实验设计：怎样避免只是在背训练任务

论文覆盖 LIBERO-Pro-10、RoboCerebra、VLABench、RoboCasa-365、SimplerEnv WidowX 和 Google 等环境，基础策略包括 MolmoAct-2、OpenVLA-7B、π0.5、RLinf-π0.5、SmolVLA、X-VLA 和 RLDX-1。

评测分三种协议：

1. **未见场景**：任务相同，但物体位置和场景布局不同；
2. **未见任务**：训练与评测任务不同，只共享底层操作技能；
3. **统一 Harness**：在跨基准的程序化任务池上优化，再到标准基准、不同机器人和动作空间上评测。

所有 Harness 最多优化五轮。编码模型是 Claude Opus 5，辅助模型包括 Qwen3、Molmo2、Qwen3-VL、Grounding-DINO、SAM 3 和 GraspGen。完整五轮平均少于 6 小时编码模型时间，成本低于 150 美元；这还不包括运行大规模机器人仿真的计算成本。

论文将相对提升报告为未见场景 **+345%**、未见任务 **+216%**。对 cross-benchmark 与 out-of-domain 设置，平均未见场景从 7.3% 提高到 58.4%，未见任务从 6.3% 提高到 48.7%。

一些单点结果更能说明 Harness 的作用：

- 通用 X-VLA 在 SimplerEnv WidowX 未见场景从 0% 到 **87.5%**，超过针对该环境微调权重的 70.8%；
- 在 VLABench 未见任务从 1.2% 到 **72.5%**；
- SmolVLA 在 RoboCerebra 未见任务从 26.0% 到 **80.0%**。

但不是每个设置都提升。RLDX-1 在 RoboCasa-365 未见场景从 27.9% 略降至 27.8%，说明接受标准只保证训练 episodes 单调提高，不能保证 held-out 永远不回退。

### 统一 Harness

统一 Harness 包裹通用 X-VLA 时：

| 评测 | Bare | Iterative Harness |
|---|---:|---:|
| 程序化训练池平均 | 1.8% | **41.6%** |
| 标准 held-out 平均 | 1.9% | **28.8%** |

包裹四个已经微调的 specialist 时，训练池平均从 58.0% 到 60.7%，held-out 从 45.9% 到 47.0%。提升较小但没有大幅破坏原能力，这与动态控制权设计一致。

### 迭代比一次性设计更重要

One-Shot 只观看 bare policy 的失败，然后生成一次 Agent 设计。后续轮次则会观看这个新 Agent 自己制造的新失败，再修正控制逻辑。大多数训练曲线随迭代稳定上升，held-out 上也几乎总是优于一次性版本。

这说明自改进不只是在同一套错误上反复“反思”，而是新版本改变了行为分布，暴露出上一轮看不到的失败模式。**执行产生新证据，新证据改变程序，程序再改变下一轮证据。**

## 与微调的真实关系

论文最吸引人的结果是某些 Harness 超过了同策略的微调版本，但不应得出“Harness 可以替代训练”的普遍结论。

微调改变模型的基础感知和动作分布，适合把大量重复技能压进权重；Harness 更适合：

- 快速修复明确、可观察的失败；
- 接入新工具和环境接口；
- 保存运行时经验；
- 在不同机器人上做适配与安全约束；
- 当权重不可访问时扩展现有模型。

最佳生产系统通常会把两者组合：权重学习通用技能，Harness 管理工具、状态、恢复与部署差异。

## 局限与风险

### 1. 全部结果来自仿真

真实机器人存在传感器噪声、网络延迟、执行误差、磨损和安全约束。一个在仿真中通过回归测试的自动生成控制补丁，可能在真实硬件上造成碰撞或过大接触力。论文尚未验证 sim-to-real。

### 2. 最多只有五轮

训练集上的提升还未明显饱和，更多轮次是否继续增益、开始过拟合，或让代码复杂度失控并不清楚。Harness 的可维护性、分支数量和技术债也没有量化。

### 3. 操作任务仍较简单

主要任务是抓取、放置、开关门、按按钮等。灵巧手操作、工具使用、柔性物体和长时序协作会产生更大的失败空间，也更难用局部程序补丁解决。

### 4. 依赖强编码模型与工具栈

系统使用 Claude Opus 5 和多个视觉/几何模型。论文没有系统比较更小编码模型、不同工具缺失、错误工具输出或 API 成本变化。结果不能简单归因于某一个算法模块。

### 5. 接受规则只看训练成绩

候选版本只要在训练 episodes 上更好就会被接受，但 held-out 已出现轻微回退。生产系统至少需要多层回归集、风险约束和复杂度惩罚，不能让成功率成为唯一合并门槛。

### 6. 自动生成控制代码带来物理安全风险

Harness 能放大动作幅度、绕过 VLA 并直接控制机械臂，这些恰恰是高权限操作。必须限制速度、力、工作空间和工具权限，并提供不可被生成代码绕过的底层安全控制器。

## 如果把它做成生产系统

我会把迭代链改造成类似软件交付的双环：

```text
失败轨迹 -> 聚类与最小复现 -> 候选补丁
-> 静态检查 -> 仿真单测 -> 回归套件 -> 安全约束检查
-> 影子运行 -> 小流量硬件验证 -> 正式版本
-> 线上异常继续回流
```

同时对 Harness 设定硬边界：

- 生成代码不能修改安全控制器和权限策略；
- 动作幅度、速度、力和空间范围由外层不可变约束裁剪；
- 每次接管必须记录原因、持续时间与恢复条件；
- 记忆写入要有置信度、来源 episode 和过期策略；
- 新版本必须在旧任务、边界条件和对抗工具输出上回归；
- 代码复杂度持续上升时，应重构而不是继续叠加补丁。

## 思考题

<details class="thought-question">
  <summary>1. Harness 超过微调模型，是否说明机器人学习不再需要更新权重？</summary>

  <div class="thought-answer">
    不能。论文中的强提升往往出现在基础策略存在明确接口错配或可编程失败时，例如夹爪一直张开、到达了错误位置、缺少侧向运动原语。Harness 用工具和控制规则能迅速弥补这些缺口，但更复杂的视觉概念、接触技能和长程策略仍可能需要权重学习。

    更准确的结论是：评估权重能力时必须把部署 Harness 也纳入系统边界。很多“需要重新训练”的故障，先用外层恢复、记忆或工具就能解决；解决不了的部分再进入数据收集和微调闭环。
  </div>
</details>

<details class="thought-question">
  <summary>2. 为什么只保证训练成绩单调提高，仍可能让 held-out 表现下降？</summary>

  <div class="thought-answer">
    新代码可能针对训练轨迹中的具体位置、物体或噪声模式形成过度专门的分支；也可能为了修复一个高频失败，改变原本在其他环境中正确的控制权分配。训练集成绩是有限样本上的代理，无法覆盖所有任务分布。

    可行的改进是维护互不重叠的优化集、回归集和安全集，接受候选时采用多目标门槛：平均成功率提高、最差任务不显著下降、碰撞和接管次数不恶化、代码复杂度受控。
  </div>
</details>

<details class="thought-question">
  <summary>3. 自动演化出来的记忆为什么比固定向量数据库更有意义？</summary>

  <div class="thought-answer">
    向量数据库只解决“存什么文本、如何找回来”。RoboArchitect 演化的是任务特定的数据结构与读写时机，例如按物体高度比例记录抓取点、按机器人记录手指闭合方向。这些状态直接对应控制变量，不需要再次把自然语言检索结果翻译成动作。

    但自发 schema 也更难治理。生产实现应为每个字段保留单位、来源、置信度、适用机器人和过期条件，防止一次偶然成功变成长期错误先验。
  </div>
</details>

<details class="thought-question">
  <summary>4. 什么时候应该让 Harness 接管，什么时候应该继续相信基础策略？</summary>

  <div class="thought-answer">
    接管条件应来自可验证的偏离信号，而不是 Harness 自己的模糊“不确定感”：例如连续若干步末端位置不变、与目标距离没有下降、夹爪状态与任务阶段矛盾、动作触碰安全边界。恢复条件同样要明确，例如完成脱困后重新询问策略，或目标进入可靠抓取区后交还控制。

    还应比较两套控制器的历史成功率与风险。原策略在熟悉任务上表现稳定时，程序只做保护；原策略在某个动作空间完全失效时，才允许更长时间的 code-as-policy 接管。
  </div>
</details>

<details class="thought-question">
  <summary>5. 怎样防止 Harness 在多轮迭代后变成不可维护的补丁堆？</summary>

  <div class="thought-answer">
    每个修改都应绑定一个可复现失败和回归测试；相似补丁应抽象为状态机或通用恢复原语；对分支数、工具调用数、平均接管时长和重复逻辑设置预算。若新版本只靠增加特例提高训练分，应拒绝合并或要求重构。

    还可以定期让独立模型做语义等价与死代码审查，并从空白 Harness 重新综合一个简洁版本，再用完整回归集与累积版本对比。自动写代码不等于可以放弃软件架构。
  </div>
</details>
