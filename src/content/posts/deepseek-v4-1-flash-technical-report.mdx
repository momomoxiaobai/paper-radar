## 一句话结论

**这份报告最值得读的不是“1M context”本身，而是四层联合设计：CED 把长 prompt 的 prefill 近似减半；CSA2 沿层维复用 global KV 与稀疏索引；FP4 把 main KV 再压一半；SWA Bounded Replay 则把短命局部缓存从长期存储中移走。四者叠加后，global KV 为 890 bytes/token、约是 V4-Flash 的 1/4，persistent KV 约是其 1/8。代价是系统变成近似稀疏检索与近似状态恢复，因此“容量达到 1M”不等于“任意 1M 证据都能稳定找回”。**

## 先建立全局认识：它到底解决哪四个问题

| 瓶颈 | 方法 | 直接改变的量 | 报告给出的结果 |
|---|---|---|---|
| 长 prompt prefill 太贵 | Causal Encoder-Decoder（CED） | prompt 经过的主干层数 | prefill 激活 8B 参数/token，复杂度约减半 |
| 每层都保存 global KV 与索引 | CSA2 | layer dimension 的缓存与 indexer 计算 | Full/Reindex/Reuse 跨层共享 |
| main KV 单项仍太大 | FP4 main KV | 每个 KV entry 的位宽 | global KV 降到 890 bytes/token |
| SWA KV 生命周期短却被长期保存 | SWA Bounded Replay | persistent cache 的内容与恢复方式 | persistent KV 约为 V4-Flash 的 1/8 |

这四个问题不能互相替代。CED 少算但不会自动减少每个 KV entry 的字节数；FP4 少存但不减少 decoder 层数；CSA2 减少 global branch 冗余，但短生命周期的 SWA KV 仍需要单独处理。

## 模型快照：先分清“总参数大”和“每 token 计算少”

| 项目 | DeepSeek-V4.1-Flash |
|---|---:|
| Backbone parameters | 552B |
| Engram conditional memory | 196B |
| Transformer | 40 层：20-layer causal encoder + 20-layer decoder |
| Hidden size | 5120 |
| MoE | 每层 1 shared + 384 routed experts；激活 6 routed experts/token |
| Activated parameters | prefill 8B/token；decode 16B/token |
| Context | 最高 1M tokens |
| SWA window | 128 |
| Sparse attention | candidate pool 16384；最终 Top-512 |

所以“Flash”不表示总参数小。它指的是：在总容量很大的前提下，把每个 token 真正触发的计算和缓存压下去。

## Method 1：CED 怎样把长 prompt 的 prefill 近似减半

### 标准 decoder-only 的浪费在哪里

普通 $L$ 层 decoder-only 模型在 prefill 时，让 $N$ 个 prompt token 穿过全部 $L$ 层，并为每层生成 K/V。Agent 场景会反复出现超长 prefill：工具返回日志、重新载入仓库、session cache miss，都可能让大段上下文重新计算。

CED 把 40 层分成两段：前 20 层是 causal encoder，后 20 层是 decoder。对 decoder 的 global attention，K/V 不再从每个 decoder layer 的 hidden state 产生，而从 encoder 最终状态直接投影：

$$
\begin{aligned}
C_l &= H_{L/2}W_l^{KV}, \\
Z_l &= H_{L/2}W_l^Z, \qquad l>\frac{L}{2}.
\end{aligned}
$$

$C_l$ 是第 $l$ 个 decoder layer 使用的 main KV，$Z_l$ 是对应的压缩/索引表示。关键不是“decoder 没有 KV”，而是 **decoder 的 global KV 不要求 prompt 依次执行所有 decoder blocks**。

### 为什么还需要 replay

CED 只绕过 global branch 的 decoder prefill。每一层仍有 Sliding-Window Attention（SWA），其局部 K/V 依赖本层 hidden state，不能直接从 encoder 最终状态投影。因此最近 $n_{\mathrm{win}}=128$ 个 token 仍需穿过 decoder，生成首批 decode 所需的局部状态。

$$
\begin{aligned}
T_{\mathrm{standard}} &= \mathcal O(NL), \\
T_{\mathrm{CED}} &= \mathcal O\!\left(\frac{NL}{2}+\frac{n_{\mathrm{win}}L}{2}\right)
\approx \mathcal O\!\left(\frac{NL}{2}\right),
\qquad N\gg n_{\mathrm{win}}.
\end{aligned}
$$

这解释了 8B/16B 的差异：大段 prompt 主要执行 encoder，生成新 token 时仍要使用完整的 decoder 路径。

## Method 2：CSA2 怎样同时压缩 KV、索引器和跨层检索

稀疏 attention 本身只回答“每层读哪些位置”。如果每层仍保存一套 main KV、indexer K 并重新扫描 1M context，缓存和索引计算仍然很大。CSA2 把压缩扩展到三个维度：

1. **Entry size**：稍后用 FP4 缩小每个 KV entry；
2. **Sequence dimension**：按 compression ratio 合并 token 位置；
3. **Layer dimension**：多个 layer 复用 main KV、indexer K 或 Top-K indices。

<figure><img src="/paper-radar/images/deepseek-v4-1-flash/csa2-modes.svg" alt="CSA2 Full Reindex Reuse 三种模式的计算与复用差异" width="1700" height="900" loading="lazy"/><figcaption>图 2：根据技术报告 Figures 4–5 重绘。三种模式都计算本层 main Q 与 SWA KV；区别在 global KV 和稀疏路由是否重算。</figcaption></figure>

### 三种模式的准确区别

| 模式 | main KV / indexer K | Top-K indices | 用途 |
|---|---|---|---|
| Full | 本层重新计算 | 扫描可见上下文，重新生成 | 建立一组可共享的 KV 与检索起点 |
| Reindex | 复用最近 Full layer 的 KV/K | 本层重新打分、重新选 Top-K | 保留检索灵活性，不重复存 KV |
| Reuse | 复用 KV/K | 复用最近 indexing layer 的 Top-K | 最便宜，多数层使用 |

Encoder 的 18 个 CSA2 layers 分成 3 组，每组 `1 Full + 5 Reuse`，compression ratio 为 2。Decoder 分成 5 组，每组 4 层：第一组 `1 Full + 3 Reuse`，后四组 `1 Reindex + 3 Reuse`，compression ratio 为 1。

### Hierarchical Sparse Indexer 为什么必要

跨层复用减少了 indexer 的次数，但 Reindex layer 若每次仍扫描 1M context，成本仍随序列长度线性增长。Decoder 的第一个 Full layer 因此先做两件事：

1. 对全部可见位置评分，并为自己选择 Top-512；
2. 以 block 最大 index score 选择 2048 个 blocks，每块保留 8 个位置，构成共享候选池。

$$
2048\ \text{blocks}\times 8\ \text{positions}=16384\ \text{candidates}.
$$

后续 Reindex layers 只在这 16384 个位置内重新选自己的 Top-512。这样深层 indexer 的搜索规模不再随 context 增长。

它的风险也很清楚：第一层若漏掉关键证据，后续层没有机会从 candidate pool 外找回。这是 1M context 最需要单独 stress-test 的地方。

## Method 3：为什么 global KV 用 FP4，SWA KV 却保留 FP8

V4.1 对 main KV 做 quantization-aware training，格式是：

- value：E2M1，约 4 bit；
- scale：每 16 channels 一个 E4M3 scale；
- 不使用 NVFP4 的第二级 global scale；
- RoPE 后量化，而不是 RoPE 前量化；
- attention 前先反量化，因此不要求硬件原生支持该 FP4 matmul。

报告给出的动态范围理由是：512-channel KV latent 经 RMS normalization 后，$\ell_2$ norm 上界约为 $\sqrt{512}\approx22.6$，训练中观察到的最大 magnitude 约为 10；E2M1 与 E4M3 scale 的范围足够，因此省掉 global scale 没测到明显精度下降。

为什么 SWA KV 不一起改成 FP4？因为局部 attention 对量化更敏感，报告继续使用 FP8。也就是说，**890 bytes/token 是 global KV 的结果，不是系统中所有 KV 都变成 FP4。**

## Method 4：SWA Bounded Replay 怎样把 persistent KV 再降 4 倍之外

V4 部署会把 global KV 与 SWA KV 都写入持久缓存，通常保留 72 小时以上。但两者复用规律不同：

| 缓存 | 真实复用周期 | V4.1 的处理 |
|---|---|---|
| Global KV | 跨请求、长尾复用 | 继续进入 persistent cache |
| SWA KV | 当前活跃会话内，分钟级 | 放在约占 host DRAM 10% 的短 TTL pool |
| SWA miss | 以前需精确重算 $L\times n_{\mathrm{win}}$ | 只 replay 最近 $n_{\mathrm{win}}=128$ tokens |

对从位置 $s$ 开始 replay 的 token $i$，它能读取的局部窗口被截成：

$$
\left[\max(s,i-W+1),\ i\right].
$$

这不是精确恢复。原始 SWA 状态可能包含 replay 起点之前通过多层传播进来的信息，Bounded Replay 会丢掉它。报告采用两种补偿：post-training 时模拟同样 replay，让模型适应；实际部署中只在 SWA cache miss 时触发。

最终 persistent KV 的约 1/8 来自两个乘法因素：不再长期保存 SWA KV，约减半；global KV 又压到 V4 的约 1/4。这里的 1/8 不能简单理解为 HBM 也减少 8 倍。

## 三个容易被忽略、但很关键的技术

### Single-Pass mHC：减少 residual-stream 的内存流量

mHC 维护 $n$ 条 residual streams。旧实现分多次完成 residual update、系数预测和 input mixing，activation traffic 约为 $(4n+4)d$。Single-Pass mHC 将 input-mixing coefficient 向后错一层：当前 block 使用上一层生成的 $A_{l-1}$，从而消除等待本层全维度 reduction 的依赖：

$$
X_{l+1}=B_lX_l+C_l\mathcal F_l(A_{l-1}X_l),
\qquad (A_l,B_l,C_l)=\mathcal H(X_l).
$$

部署时 Mega-mHC 把 residual update、input mixing、coefficient prediction、pre-norm 与 FP8 conversion 融合到一个 kernel，达到约 $(2n+2)d$ 的读写量，接近理论下界，相对原实现约减半。

### Engram：把记忆容量从 Transformer 计算中分离

196B Engram 参数均分到两个模块，使用 2/3/4-gram、8 个 hash heads，每个 head 约 16M entries。它用 tokenizer compression、multi-head hashing、context-aware gating 和 multi-branch integration 查表；embedding table 与 key/value projection 使用 FP8。

核心思想是：静态或组合性记忆通过确定性地址查表，而不是每次都经过 MoE 计算。表可以提前从 host memory 通过 RDMA prefetch，与 backbone 计算重叠。报告没有给出足够独立的 Engram 消融，因此它的精确贡献仍难从整套系统中剥离。

### DSpark：用 3 层 drafter 一次提议 5 个 token

DSpark 是 speculative decoder：3 个 Transformer blocks、128-token sliding window，一次并行产生 5 个 draft positions；Markov head 建模 draft token 依赖，confidence head 预测各位置被接受的概率，再结合系统负载动态选择 verification length。

它在 pretraining 后单独训练，此时 backbone 冻结；post-training 时与 backbone 一起继续适配，但 DSpark loss 不反传进 backbone。这样它既能加速线上 decoding，也能加速 RL/OPD 的 rollout generation。

## 关键实验 1：缓存和计算到底省了多少

| 指标 | V4.1-Flash | 对照/解释 |
|---|---:|---|
| Activated params / prefill | 8B | V4-Flash 13B；V4-Pro 49B |
| Activated params / decode | 16B | CED 只重点优化 input-heavy prefill |
| Global KV | 890 bytes/token | 约 V4-Flash 的 1/4 |
| Persistent KV | 约 V4-Flash 的 1/8 | global KV 1/4 × 移除长期 SWA KV约 1/2 |
| Context | 1M | 34T tokens 后开始 context extension |
| Reuse-mode kernel flow | prefill 15 kernels；decode 11 kernels | 来自融合后的 inference implementation |

这张表证明了“状态体积变小”，但报告没有给出一张完整的端到端 serving latency、tokens/s、并发量和功耗对照表。因此不能从 1/4 KV 直接推出吞吐提高 4 倍，也不能从 prefill 复杂度减半直接推出所有请求延迟减半。

## 关键实验 4：同一模型换 Harness，分数会差多少

| Benchmark | 最低配置 | 最高配置 | 差距 |
|---|---:|---:|---:|
| DeepSWE v1.1 | OpenCode 65.5 | mini-SWE 74.2 | 8.7 pp |

因此 Agent benchmark 应理解为：

$$
\text{score}=f(\text{model},\text{harness},\text{tools},\text{context policy},\text{verifier}).
$$

## 关键实验 5：Reasoning effort 是连续控制，不是三套模型

系统 prompt 加入 $b\in\{1,\ldots,100\}$。对每个 $(x,b)$ 单独构造 group-relative advantage，跨 effort 的响应不直接比较；长度 penalty 随 effort 指数下降：

$$
\begin{aligned}
z^{(b,j)} &\sim \pi_\theta(\cdot\mid x,b), \\
r_{\mathrm{len}}^{(b,j)}
&=-\min\!\left(C_{\max},k(b)\frac{\ell_{b,j}}{L_{\mathrm{norm}}}\right), \\
k(b)&=k_0\exp\!\left(-\frac{b-b_{\min}}{\tau}\right).
\end{aligned}
$$

从 effort 25 到 100：

| 任务 | effort 25 | effort 100 | 变化 |
|---|---:|---:|---:|
| 8 个 reasoning benchmarks 平均 | 67.1 | 76.3 | +9.2 pp |
| DeepSWE v1.1 | 66.0 | 74.2 | +8.2 pp |
| Terminal-Bench 2.1 | 82.4 | 90.6 | +8.2 pp |
| 平均 output tokens | 1× | 约 2.5× | 成本显著增加 |

收益主要集中在 60–80；从 80 提升到 100，Agent trajectory 会增长约 1.6–1.8×，精度只小幅提高。公开 API 的 low/high/max 对应 50/75/100。

## Multi-agent：有提升，但不是免费并行

Agent Team mode 允许 lead 创建持久 teammate、共享 checkout，并通过 mailbox 异步通信。训练 reward 除任务表现外，还加入 collaboration bonus 与 derived-latency penalty；后者把事件依赖建成 DAG，以 critical path 衡量真实协调成本。

ProgramBench golden subset 上，多 Agent 在 8 小时达到 **30.04%**，单 Agent 为 **20.39%**；FrontierSWE v2 no-GPU 在 20 小时为 **32.90% vs 28.20%**。这是初步实验，而且用最长 20 小时 rollout 换取提升，不能只看最终分数。

## 这份报告真正证明了什么，没有证明什么

### 证据较强的部分

- 架构上确实把 prefill 激活、global KV 与 persistent KV 分别压低；
- Base 代码能力和大批 Agent benchmarks 相对 V4-Flash 明显提升；
- reasoning effort 能在一套 checkpoint 上形成平滑成本-质量曲线；
- Agent 能力可跨多个 harness 迁移，不完全依赖单一脚手架。

### 仍缺关键证据的部分

- 没有统一的端到端 serving latency、吞吐、并发、能耗对照表；
- CED、CSA2、FP4、Engram、DSpark 的独立能力消融不够完整；
- Bounded Replay 只报告“影响可忽略”，缺少针对 cache-resume 边界的系统 stress test；
- 1M context 的检索、组合推理与 candidate-pool recall 没有足够细的外部可复现评测；
- 45T tokens、内部工作流数据和 DSec 基础设施难以由外部完整复现。

## 工程启示

- 长 prompt Agent 首先要分解成本：prefill FLOPs、HBM KV、persistent cache、decode throughput 是四张不同的账。
- Sparse attention 的线上监控不能只有 perplexity；应记录 candidate recall、Top-K stability 和关键证据漏检。
- 缓存应按复用时间尺度分层。分钟级 SWA 与 72 小时 global prefix 不应共享同一 SSD policy。
- Bounded Replay 类近似必须在训练中模拟，并单独测试 cache hit position、短 suffix、频繁多轮和极端依赖链。
- Benchmark 报告必须带 harness 版本；同一模型仅换脚手架就能波动 6–9 个百分点。
- Reasoning effort 更适合做任务路由：普通任务用 60–80，最高档只给真正困难且高价值的任务。

## 思考题

<details class="thought-question"><summary>1. CED 为什么能把 prefill 激活降到 8B，但 decode 又回到 16B？</summary><div class="thought-answer">长 prompt 主要通过 20 层 encoder；decoder global KV 直接从 encoder 最终 hidden 投影，不必让所有 prompt token 穿过 20 层 decoder。生成新 token 时仍需执行 encoder/decoder 相关路径和完整 decode 计算，因此激活量回到约 16B。优化针对输入重、输出相对短的 Agent 工作负载。</div></details>

<details class="thought-question"><summary>2. 890 bytes/token 为什么不能直接推导“1M context 只需 890 MB”？</summary><div class="thought-answer">890 bytes/token 是 global KV footprint，实际服务还包括 SWA KV、scale/index、hidden/temporary buffers、batch metadata、模型权重、并发请求碎片与 replay workspace。它可估 HBM 主项，但不是完整进程显存。还需区分 HBM resident 与 SSD/host persistent cache。</div></details>

<details class="thought-question"><summary>3. Bounded Replay 的近似为什么可能在普通 benchmark 中看不出来？</summary><div class="thought-answer">大多数任务对最近 128 tokens 的局部状态足够，或者 global sparse attention 能补回远处信息。真正风险集中在 cache-hit 边界：答案依赖更早 SWA 链式传播、短 suffix、精确位置状态时。随机平均 benchmark 会稀释这些尾部案例，因此需要定向 stress tests。</div></details>

<details class="thought-question"><summary>4. 报告说 post-training 没有新算法，这是否意味着 RL 不重要？</summary><div class="thought-answer">不是。RL 仍是把任务表现写入 policy 的优化机制；“没有新算法”表示边际提升主要来自任务/环境/verifier 的规模与质量，而非更新方程创新。没有可验证环境，标准 RL 也学不到可靠 Agent 行为；反过来，再复杂的 RL 也救不了可被 hack 的 verifier。</div></details>

<details class="thought-question"><summary>5. reasoning effort 的指数 penalty 为什么比线性 penalty 更自然？</summary><div class="thought-answer">若额外 token 的边际效用随长度递减，低 effort 应对每个 token 收更高成本，高 effort 再逐渐放松。指数系数始终为正、比例变化平滑，增加固定 effort 间隔带来固定倍数的 penalty 下降，便于跨 1–100 插值。线性下降可能在高 effort 变负或在低端分离不足。</div></details>

<details class="thought-question"><summary>6. 如何公平验证“1M context”不是营销数字？</summary><div class="thought-answer">至少同时测：不同深度的 needle retrieval、多个相互冲突证据、需要组合远距片段的任务、cache hit/miss 与 bounded replay 边界、长输入下的答案质量和延迟/显存。还应对比 full attention 或更高成本配置，分开报告能接收、能检索、能推理和能经济部署四个层次。</div></details>
